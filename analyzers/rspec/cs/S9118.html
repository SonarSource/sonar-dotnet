Passing a value of an incompatible type as a default value for an entity property or migration column can silently produce a broken schema, or fail inconsistently depending on the database provider, because EF Core’s default-value APIs accept the value as object? and give no compile-time type safety.

Why is this an issue?

EF Core’s default-value APIs — PropertyBuilder(<T>).HasDefaultValue(), MigrationBuilder.AddColumn(), MigrationBuilder.AlterColumn(), and ColumnsBuilder.Column() — all type their defaultValue/value parameter as object?, never as the property’s or column’s actual CLR type. The C# compiler therefore gives no static safety here: any value can be passed, and there is no compile-time signal when it does not match the target type.

EF Core’s own runtime handling of a type-incompatible default value is neither complete nor consistent:

  • Some mismatches, such as a string passed for a Guid property, are caught immediately with a clear InvalidOperationException the first time the model is built.
  • Other mismatches, such as an int passed for a string property, pass model validation silently.
  • At the stage where the default value is turned into a SQL literal, behavior is provider-dependent: the same mismatch throws on one provider and produces a bogus literal on another. For example, an int default for a Guid column throws InvalidCastException on SQLite but silently succeeds on SQL Server.

That same loosely typed default value is round-tripped through EF Core’s type-mapping machinery twice: once when the schema or migration is generated, and again when the database’s default is materialized back into the CLR property while reading a row. Passing a mismatched type is inherently fragile — whether it happens to work today depends on the current provider and EF Core version, and it can silently stop working after a provider change, an EF Core upgrade, or a schema or migration regeneration.

What is the potential impact?

A type mismatch that is not caught by EF Core can produce a database column whose default value does not match its declared type. For example, an int default value of 42 supplied for a string column can silently create the following schema, with no error raised anywhere in the process:

"Label" TEXT NOT NULL DEFAULT '42'

Whether a given mismatch fails at write time, fails at read time, or does not fail at all, is provider-dependent and cannot be reliably predicted from the code alone.

How to fix it

Make sure the value passed as a default matches the CLR type of the target property or column. When in doubt, verify the resulting schema explicitly, for example by inspecting a generated migration or reviewing context.Model, instead of relying on EF Core to flag an incompatibility.

Code examples

Noncompliant code example

public void Configure(EntityTypeBuilder<Widget> builder)
{
    builder.Property(x => x.Label) // Label is a string property
        .HasDefaultValue(42); // Noncompliant: int passed as default value for a string property
}

Compliant solution

public void Configure(EntityTypeBuilder<Widget> builder)
{
    builder.Property(x => x.Label) // Label is a string property
        .HasDefaultValue("42");
}

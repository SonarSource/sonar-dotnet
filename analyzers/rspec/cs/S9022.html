An Include or ThenInclude call can be entirely inert: Entity Framework Core generates the exact same SQL with or without it.

Why is this an issue?

Include and ThenInclude tell Entity Framework Core to eagerly load a related navigation together with the entity that owns it. In each of the following cases, that instruction has no effect on the generated SQL — it adds nothing but noise, and can safely be removed:

  • it repeats a navigation path already included elsewhere in the query, without adding a ThenInclude that goes deeper than the earlier call. Entity Framework Core resolves the navigation path of every Include/ThenInclude call and merges calls that resolve to the same path into a single join.
  • a Select, SelectMany, or Join further downstream projects the same navigation directly — bare, or wrapped in an anonymous type or constructor call. Entity Framework Core materializes that navigation because the projection asks for it, independently of any Include.
  • the query ends in an aggregate or scalar operator — such as Count, Sum, Any, All, Average, or Max/Min with a selector, and their async equivalents — that never returns the entity at all. An Include only affects entities the query actually returns.

In every case, it can also mislead a reader into thinking it changes what is loaded.

Exceptions

The rule does not apply when:

  • the repeated Include call re-anchors the chain before a different ThenInclude. Entity Framework Core has no syntax for attaching two different ThenInclude continuations to one Include, so repeating it is the idiomatic way to load two independent nested navigations or collections.
  • one of the calls applies a filter (through Where, Skip, Take, or similar) that the other does not carry, regardless of which one is written first — removing the filtered call would change which rows are loaded.
  • the Include carries a customization (Where, OrderBy, Skip, Take, or similar) that the downstream projection does not reproduce — see {rule:csharpsquid:S9023}, which covers that case.

How to fix it

Remove the Include (or ThenInclude) call that has no effect.

Code examples

Noncompliant code example

var students = await context.Students
    .Include(s => s.Enrollments) // Noncompliant: "Enrollments" is already included below
    .Include(s => s.Enrollments)
    .ToListAsync();

Compliant solution

var students = await context.Students
    .Include(s => s.Enrollments)
    .ToListAsync();

This repeated Include is not redundant — it branches into two different ThenInclude calls:

var students = await context.Students
    .Include(s => s.Enrollments).ThenInclude(e => e.Course)
    .Include(s => s.Enrollments).ThenInclude(e => e.Student) // Compliant: re-anchors before a different ThenInclude
    .ToListAsync();

An Include is redundant the same way when a projection further down the query already returns the navigation directly:

var students = await context.Students
    .Include(s => s.Enrollments) // Noncompliant: "Enrollments" is already returned by the projection below
    .Select(s => new { s.LastName, s.Enrollments })
    .ToListAsync();

var students = await context.Students
    .Select(s => new { s.LastName, s.Enrollments })
    .ToListAsync();

It is also redundant when the query never returns the entity at all:

var studentCount = await context.Students
    .Include(s => s.Enrollments) // Noncompliant: this "Include" has no effect; the following call to "CountAsync" never returns the entity
    .CountAsync();

var studentCount = await context.Students
    .CountAsync();
